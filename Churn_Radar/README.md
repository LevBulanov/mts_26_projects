# ChurnRadar — сверхбыстрый скоринг оттока клиентов телеком-оператора

Бинарная классификация оттока клиентов (LightGBM) с акцентом на **production-инференс**: скоринг одной записи за доли миллисекунды на одном ядре CPU и label-free мониторинг дрифта входных данных и предсказаний.

Итоговая работа по модулю ML.

---

## О проекте

Задача — по обфусцированным данным о поведении клиента (пополнения, трафик, звонки, тарифы, пакеты) предсказать, уйдёт ли клиент (`binary_target`).

Ключевые ограничения, под которые строилось решение:

- метрика качества — **F1** (порог по тесту: 0.65);
- функция `get_score(dict_input)` обрабатывает **одну строку** и укладывается в лимит **0.1 мс**;
- в продакшене доступно **1 ядро CPU**;
- истинные метки в проде неизвестны, поэтому качество отслеживается через дрифт признаков и долю положительных предсказаний.

## Результаты

| Метрика | Значение |
|---|---|
| OOF ROC-AUC (5-fold) | **0.9031** |
| OOF PR-AUC | **0.6483** |
| OOF F1 | **0.6521** |
| Test F1 | **0.6501** |
| Порог классификации | **0.341** (среднее по фолдам) |
| Число деревьев / `num_leaves` | 100 / 81 |

Самый важный признак — `секретный_скор`, с большим отрывом от остальных. Далее идут `объем_данных`, `avg_check`, `arpu_per_freq`, `data_voice_ratio`.

Датасет по оттоку клиентов (`train.csv`, `test_full.csv`), данные обфусцированы: регионы заменены, счётчики прошли через извлечение корня.

| `доход` | доход с одного клиента в месяц |

## Как это работает

### 1. Feature engineering

- **Флаги пропусков** по 10 колонкам + их сумма (`flags_sum`) — пропуск сам по себе несёт сигнал.
- **Парсинг строки `pack`** регулярными выражениями: сегмент (b2b / vas / social / promo / regular), тип услуги, направление, периодичность, трафик в МБ, длительность в днях, признаки безлимита, число токенов и др.
- **Восстановление счётчиков**: обфускация брала корень, поэтому признаки возводятся в квадрат (`raw_freq`, `raw_data`, `raw_onnet`, …).
- **Производные признаки**: средний чек, ARPU на частоту, доля продуктов в активности, соотношение data/voice, зональная активность, эффективность и интенсивность пакета, индикаторы низкой/высокой активности.
- **Категориальные признаки** кодируются `CatBoostEncoder` (защита от утечки таргета).

### 2. Модель и подбор гиперпараметров

- **LightGBM**, 5-fold `StratifiedKFold`, out-of-fold оценка.
- Гиперпараметры подобраны **многокритериальным Optuna**: максимизация F1 и минимизация сложности модели (`num_leaves × n_estimators`). Это даёт Парето-фронт, из которого выбрано решение, укладывающееся в лимит по времени.
- Порог для F1 подбирается по OOF-предсказаниям и усредняется по фолдам.
- Финальная модель обучена на всех данных (100 деревьев).

### 3. Инференс под одну строку (< 0.1 мс)

Pandas-пайплайн полностью вынесен из горячего пути:

- модель скомпилирована в нативный код через [**lleaves**](https://github.com/siboehm/lleaves) (LLVM);
- `prepare_row` — переписанная на чистом Python версия `prepare()` для одного `dict`; идентичность признаков проверена на 1000 примеров;
- `CatBoostEncoder` выгружен в плоские словари, кодирование — один `dict.get` с дефолтом для неизвестных категорий;
- переиспользуемый `numpy`-буфер (`_BUF`) — ноль аллокаций на вызов;
- предкомпилированные регулярки и `lru_cache` на парсинг `pack`;
- заполнение буфера сгенерировано метапрограммированием (линейный код без циклов);
- предсказание строго в один поток: `predict(..., n_jobs=1)`.

### 4. Мониторинг без меток (`InputDriftMonitor`)

Класс отслеживает качество в проде, не зная `y_true`:

- **PSI** по числовым (квантильные бины train) и категориальным признакам;
- **доля предсказанных «1»** с 3σ-доверительным интервалом;
- **KS-статистика** (лениво, только при PSI ≥ warn);
- **unseen rate** — доля новых категорий;
- скользящие окна, снапшот раз в `step` событий, накладные расходы ≈ **6 мкс/событие**;
- визуализации: доля позитивов, PSI по окнам, heatmap PSI по признакам.

**Что показал мониторинг на тесте (994 окна по 500 записей):**

- доля предсказанных «1» стабильна (0.244 против 0.244 на train);
- 15 из 17 признаков ни разу не превысили alert-порог PSI 0.25;
- дрифт зафиксирован в `зона_1` и `зона_2` (алерты в 34% окон);
- новых категорий практически нет.


### 5. Пример вызова скоринга:

```python
result = get_score({
    "client_id": 1,
    "регион": "...", "использование": "...",
    "сумма": 100.0, "частота_пополнения": 3.0, "доход": 50.0,
    "сегмент_arpu": 120.0, "частота": 5.0, "объем_данных": 4.0,
    "on_net": 2.0, "продукт_1": 1.0, "продукт_2": 0.0,
    "зона_1": 0.0, "зона_2": 0.0, "mrg_": 0,
    "секретный_скор": 0.5, "pack": "no_pack", "pack_freq": 0.0,
})
# {"client_id": 1, "prediction": 0}
```

> Подбор Optuna занимает много времени (запускался на Kaggle), поэтому в ноутбуке он закомментирован, а найденные `best_params` зашиты в код.
